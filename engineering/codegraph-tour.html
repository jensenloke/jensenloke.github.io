Know What Breaks Before You Change It

A tour of CodeGraph - the cross-layer dependency graph we query before touching a stored procedure, a table, an endpoint, or a shared component - and why coding agents need blast radius even more than we do.

Jensen Loke · September 2026 · ~7 min read

Public note: this article describes our tooling and operating practice in general terms. Product and customer names are generalized, and command examples are simplified. The pattern is the point, not the internals.

The blast-radius problem

Change one stored procedure and something breaks - the question is whether you find out in review or in production.

Our stack is sixteen products wide and five layers deep: Angular frontends, C# backends, SQL Server databases, Jasper reports, and - still running real workflows - legacy VBA forms from codebases that predate most of the team. A single business concept lives in all of them at once: a policy table is read by stored procedures, called by endpoints, rendered by components, printed by reports, and mirrored in a twenty-year-old Access form.

In a stack like that, "obvious" changes have non-obvious consequences. Renaming a column is never just a rename. Dropping an endpoint that looks unused can break a legacy form nobody remembers shipping. And the consequences are cross-layer: the thing that breaks is rarely in the layer you edited.

Coding agents make this sharper, not softer. They change code faster than a human can trace the fallout - thirty files in a minute is a normal session. Speed is the whole point of using them, so the safety question becomes: how do you know the blast radius before the change lands?

One graph, every layer

CodeGraph is a local dependency database with a CLI. Indexers walk each layer and emit one graph: nodes for everything that can be depended on, edges for every dependency.

Angular

Components, services, routes - including which inputs each call site actually passes.

C#

Functions, API endpoints, services, classes across the backend projects.

SQL

Stored procedures, tables, views, functions - from the system catalogs.

Reports

Jasper templates, so a data change shows up in what gets printed.

Legacy VBA

Forms, reports, queries, modules extracted from the old Access frontends.

The current index holds 41,440 nodes and 179,234 edges across the sixteen products. The part that matters most is the bridging: five legacy customer codebases and the modern stack resolve onto shared nodes, so one table can show you its legacy VBA forms and its modern C# endpoints in a single view. That cross-layer visibility is the whole product - a per-repository tool would miss exactly the edges we care about.

The core loop: blast before you edit

Four steps, run before and after any risky change.

01

Identify

Find the node you are about to touch - by name, layer, product, or keyword search.

02

Query

Run the narrowest useful command: blast for full impact, upstream for what breaks, downstream for what it depends on, flow for the execution path.

03

Summarize

Write down the affected upstream and downstream code and the cross-layer risks - before editing anything.

04

Re-verify

After the edit, rerun a focused query to confirm the dependencies you expected still resolve.

A typical pre-change check reads like this: blast the stored procedure you are about to modify; read the upstream list (every caller, in every layer); skim the execution flow from the entry point to the procedure. Ten seconds of querying replaces an hour of grep-and-hope - and grep cannot see across layers anyway.

The questions it answers

Each command is a question you would otherwise answer by reading code you have never seen.

Question Command What you get
What breaks if I change this? blast <node> Full upstream and downstream impact, every layer.
Who calls this? upstream <node> Every dependent - including the legacy ones.
What touches this table? table <name> All code and SQL that reads or writes it.
Is this shared component safe to edit? consumers <Component> Every renderer, and which inputs each call site actually passes.
What did my changes just touch? diff [git-ref] Changed files mapped to graph nodes and their blast radius.
What would a rename break? rename <old> <new> Every reference that needs updating, before you start.
Is this endpoint really unused? unused Dead endpoints - with the confidence that nothing, in any layer, calls them.

The consumers command deserves special mention. Shared Angular components fail in a specific, nasty way: you guard a behavior change behind an @Input that most call sites never pass. consumers lists every component that renders the target and which inputs each one actually supplies - it catches "I guarded my change on an input that thirteen of fifteen screens never pass" before review does.

Why agents need it more than we do

A human edits one file and holds the blast radius in their head. An agent edits thirty and holds nothing - unless you give it a tool that answers the question.

In our operating model, the rule is explicit: CodeGraph comes first - before database queries, before code changes, before any cross-layer work. The graph is what makes that rule executable instead of aspirational. The agent runs blast, reads the result, and only then proposes the change; the blast radius becomes part of the plan, not part of the post-mortem.

Two commands matter most in agentic sessions. diff maps the agent's own changes back onto the graph - "you touched these nodes; here is what depends on them" - which turns a thirty-file diff into a reviewable impact statement. And blast before a change is the difference between an agent that asks permission with evidence and one that asks forgiveness from production.

This is the same thesis as the knowledge management layer: retrieval tells an agent what the codebase contains; a dependency graph tells it what the codebase owes to each piece. Agents that know what they might break are the ones you can trust with write access.

What it changes in practice

Three decisions that go differently once the graph answers first.

The rename that didn't happen

A table rename looked safe in the modern code. The graph showed legacy VBA queries referencing it by the old name in three products. Decision: alias, don't rename.

The "unused" endpoint that wasn't

An endpoint with no modern callers was queued for deletion. Upstream analysis found a legacy form calling it directly. Decision: keep it, document it.

The shared component that got a new input

A behavior change to a widely-rendered component would have silently altered screens that never opted in. The consumers list made the opt-in explicit. Decision: new input, default to old behavior.

None of these were exotic. They are the ordinary, daily near-misses of a multi-layer codebase - the kind that used to surface as support tickets a week after a release. The graph moves them to before the edit, where they cost ten seconds instead of a week.
